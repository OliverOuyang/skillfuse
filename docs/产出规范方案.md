# Skill 产出规范方案

> 一句话：给所有 skill 的产出定一套统一的目录和版本规则，让「这次比上次好在哪」变成可以直接查出来的事实。

---

## 一、现在的问题

我们已经有一批 skill 在跑，但**产出是散的**：

| 现状 | 后果 |
|---|---|
| 每个 skill 自己决定把文件写到哪、叫什么名字 | 跑完要人工翻目录才找得到交付物 |
| 没有版本概念，重跑直接覆盖 | 调优后「改好了还是改坏了」说不清，只能凭印象 |
| 一次任务调了好几个 skill，产出混在一起 | 谁的输出喂给了谁、中间哪步出错，回溯不了 |
| 跨对话做同一个课题 | 每次都是从零开始，历史结果找不回来 |

根子上是一件事：**产出没有契约**。skill 的输入我们管得挺严（有 IO 规范、有 trace 契约），输出却是自由发挥。

---

## 二、方案：一个 skill 搞定，使用者零学习成本

我们做一个叫「**产出管家**」的 skill。使用者要做的只有一件事：

> 在项目根目录下，跟 AI 说一句「用产出管家整理这次的产出」，或者干脆什么都不说——它会在其它 skill 干活时自动接管。

剩下的建目录、起名字、编版本号、记台账、查合规，全部由这个 skill 自己完成。**不需要记任何命令。**

### 内部怎么分工

| 层 | 负责什么 |
|---|---|
| **业务 skill** | 只声明「我产出什么」——主交付物是哪个、附带哪些数据。不管写到哪 |
| **产出管家 skill** | 规范 + 工具打包在一起：规则写在说明里，脚本放在它自己的 `scripts/` 下 |
| **SkillFuse 检查** | 事后体检：目录对不对、台账全不全、有没有漏 |

关键取舍：**不让 AI 做确定性的事**。让模型去推理「该建哪个目录、版本号是几」，十次会错三次；把这部分变成管家 skill 里的一段脚本，一次都不会错。模型只负责它擅长的业务内容。

---

## 三、产出目录长什么样

三层结构，名字都用中文，扫一眼就知道是什么：

```
产出/
└── 【课题】Q3风险复盘/                  ← 一个业务需求，可以跨好几天、好几次对话
    ├── 课题说明.md                        目标是什么、验收标准、进展到哪了
    │
    ├── 第1次执行_0922上午/               ← 一次对话 = 一次执行
    │   ├── 本次说明.md                     这次干了什么、用了哪些 skill、结论
    │   ├── 我的需求/                       需求原文、上传的附件
    │   ├── 最终交付/                       这次任务对外给出的东西
    │   └── 各环节产出/
    │       ├── 取数/
    │       │   └── 第1版/
    │       └── 风险报告/
    │           ├── 第1版/                   第一次生成
    │           └── 第2版/                   调完重跑，第1版原样保留
    │
    ├── 第2次执行_0923上午/               ← 隔天换个对话继续，同一课题
    │   └── 各环节产出/风险报告/第3版/
    │
    └── 版本对比/                          ← 把同一个 skill 的历次产出串成一条线
        └── 风险报告/
            ├── 第1版          （索引文件，指向 第1次执行_0922上午/…/第1版）
            ├── 第2版          （索引文件，指向 第1次执行_0922上午/…/第2版）
            ├── 第3版          （索引文件，指向 第2次执行_0923上午/…/第3版）
            └── 最新版          （索引文件，指向 第3版）
```

每个「第 N 版」里面固定四个区，也都是中文：

```
第2版/
├── 产出台账.json      这版是谁产出的、用了什么输入、上一版是哪个、指标多少
├── 报告/              人看的交付物（md / html / Excel）
├── 数据/              机器读的中间数据（csv / json）
├── 执行记录/          每一步做了什么、花了多久、哪步失败（沿用已有 trace 契约）
└── 日志/              原始运行日志，排查问题时才看
```

> 目录名是给人看的，中文；机器识别靠 `产出台账.json` 里的标准 ID，两边不打架。

### 三个关键设计

1. **重跑不覆盖，版本递增**——第1版、第2版、第3版并存，随时回到任何一版。
2. **跨对话的同一课题归在一起**——不同对话是不同的「第 N 次执行」（上下文互不污染），但「版本对比」目录把它们串成一条线。
3. **每一版都记着上一版是谁**——这是调优闭环的关键，「第2版比第1版改了什么、指标涨了多少」可以自动算，不用人工比对。

> 「版本对比」下放的是**索引文件**而不是软链：软链在 Windows 需要额外权限、跨平台复制时会断，索引文件哪里都能读。

## 四、不同场景下目录长什么样

### 场景 1：只跑一个 skill，跑一次

最简单的情况，结构也不特殊化，保持一致：

```
产出/【课题】周度获客复盘/
├── 课题说明.md
└── 第1次执行_0923上午/
    ├── 本次说明.md
    ├── 我的需求/需求.md
    └── 各环节产出/获客分析/第1版/
        ├── 产出台账.json
        ├── 报告/获客复盘.md        ★ 主交付物
        ├── 数据/渠道明细.csv
        └── 执行记录/
```

### 场景 2：同一个 skill 反复调优

调三次就是三版，全部留着：

```
└── 第1次执行_0923上午/各环节产出/获客分析/
    ├── 第1版/    初稿，发现口径不对
    ├── 第2版/    调了口径，基线=第1版
    └── 第3版/    补了归因，基线=第2版   ★ 最终采用
```

「基线」写在台账里，所以随时能问：第3版比第1版到底好在哪。

### 场景 3：一次任务里 AI 编排多个 skill

各 skill 的产出各归各的，互不干扰；汇总件单独放：

```
└── 第1次执行_0923下午/
    ├── 本次说明.md                    编排顺序 + 各 skill 用了哪一版
    ├── 我的需求/
    ├── 最终交付/Q3风险复盘.html      ★ 对外交付的汇总件
    ├── 执行记录/                       编排层的记录：谁先谁后、哪步失败
    └── 各环节产出/
        ├── 取数/第1版/                跑了 1 次
        ├── 风险报告/
        │   ├── 第1版/
        │   ├── 第2版/
        │   └── 第3版/                 跑了 3 次才满意
        └── 图表生成/第1版/            跑了 1 次
```

注意各 skill 版本数**不齐**很正常——取数一次过，报告改了三遍。「本次说明」里记的是最终采用的那一版。

### 场景 4：跨对话做同一个课题

这是最容易乱的场景，规则是：**不同对话 = 不同「第 N 次执行」，但归在同一课题下**。

```
产出/【课题】信贷模型调优/
├── 课题说明.md                      累计进展、已试过的方案
├── 第1次执行_0920上午/              周一的对话
│   └── 各环节产出/模型评估/第1版/ 第2版/
├── 第2次执行_0922下午/              周三，换了特征再试
│   └── 各环节产出/模型评估/第3版/
├── 第3次执行_0923上午/              周四，调参
│   └── 各环节产出/模型评估/第4版/ 第5版/
└── 版本对比/模型评估/
    第1版 第2版 第3版 第4版 第5版 最新版
```

隔离保住了（每次对话的上下文、输入、记录互不污染），对比也保住了（版本线从第1版连到第5版，跨对话可比）。

### 场景 5：一个 skill 内部调用了另一个 skill

嵌套时结构递归，一层套一层，一眼看得出从属关系：

```
└── 各环节产出/
    └── 风险报告/第2版/
        ├── 报告/  数据/  执行记录/
        └── 内部调用/
            └── 取数/第1版/
```

### 场景 6：中途失败了

失败的版本**不删除**，台账里标明状态，方便复盘：

```
└── 各环节产出/风险报告/
    ├── 第1版/    状态：失败（取数超时）
    ├── 第2版/    状态：部分完成（报告生成了，图表缺失）
    └── 第3版/    状态：成功            ★ 最终采用
```

### 场景 7：临时跑一下，没想好算哪个课题

不强制使用者先想清楚，自动进临时区，事后可以一键归并：

```
产出/
├── 【临时】0923随手跑/
│   └── 第1次执行_0923下午/…
└── 【课题】Q3风险复盘/               ← 后面觉得有用，可以整体搬过来
```

## 五、使用起来是什么样

### 做事的人

正常干活，一句话开个课题就行：

```
「开个课题叫 Q3风险复盘，接下来的产出都放这儿」
「这次的报告和上一版比，好在哪？」
```

第二句话会得到：

```
风险报告  第2版 vs 第1版

规范得分    0.79  →  0.86   ↑
契约通过    否    →  是
执行耗时    42秒  →  38秒
变更文件    报告/main.md、数据/scored.csv
新增内容    「相比上一版变化」章节
```

### AI

调用产出管家 skill，它内部依次完成：**开目录 → 交给业务 skill 写内容 → 记台账 → 更新版本线**。AI 不需要理解目录规则，也不需要拼路径。

---

## 六、这件事带来什么

| 价值 | 具体是什么 |
|---|---|
| **说得清效果** | 每次调优都有前后对比数据，不再靠「感觉好像好点了」 |
| **出事查得到** | 一次任务用了哪些 skill、哪一版、谁喂给谁，全在台账里 |
| **能防回退** | 新版本指标掉了，检查环节直接报出来，不会悄悄上线 |
| **资产沉淀** | 同一课题的历史产出可复用、可继承，不用每次从零开始 |
| **零学习成本** | 使用者不用记命令、不用背目录规则，一个 skill 全包 |
| **接得上现有体系** | 复用已有的 trace 契约和 SkillFuse 检查引擎，不是另起炉灶 |

## 七、落地计划

| 阶段 | 内容 | 产出 | 状态 |
|---|---|---|---|
| **一期** | 做「产出管家」skill（规范 + 脚本打包在一起） | 可直接用的 skill | ✅ 已完成 |
| **二期** | 接入 SkillFuse 检查，新增「产出规范」分类 | 检查页多一类，**先提示不拦截** | ✅ 已完成 |
| **三期** | 版本对比能力 | 「和上一版比好在哪」一句话出结果 | ✅ 已完成 |
| **四期** | 存量 skill 迁移，规则转强制 | 每个 skill 补约 10 行产出声明 | ⬜ 待推进 |

一到三期的验收情况：七个场景加三项边界共 10 个端到端测试全部通过；产出管家用 SkillFuse 检查自己得 97/100（33/34 条规则通过）。

**成本**：剩余成本主要在四期——存量 skill 各补一小节声明，单个约 10 分钟。

**风险控制**：新规则先只提示不拦截，等存量迁移完再转强制，不会一夜之间让现有流程全部报红。

---

## 八、需要拍板的事

1. **产出根目录放哪**：建议放仓库内，台账（几 KB 的 JSON）进 git 便于追溯评审，大文件（csv/Excel/图片）不入库。
2. **目录命名用中文还是英文**：建议中文，可读性优先；机器识别靠台账里的标准 ID，不受影响。
3. **推进节奏**：建议一期先做，拿 2–3 个 skill 试点跑通再全面铺开。
